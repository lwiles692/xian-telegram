> 本目录是 [`spec-v4.md`](../../../spec-v4.md) 的落地执行计划。规格负责明确范围、规则和验收目标，本目录负责明确实施顺序、文件边界、测试方法、发布门槛和回滚边界。

## 一、计划使用说明

### （一）执行原则

1. 按 M0→M1→M2→M3→M4A→M4B→M5→M6A→M6B 的顺序实施；不得在前置数据模型和数值档未稳定时提前开放下游玩法。
2. 每个任务均按“先写失败测试、确认失败、最小实现、相关测试、完整回归、提交”执行。
3. 每次提交前必须运行 `.venv/bin/python -m pytest`；涉及数值、掉落、产销或战斗门槛的任务还必须运行 `.venv/bin/python -m tools.balance_sim`。
4. 所有状态变更按钮继续使用 `action_callback_data()` 与 `consume_action_callback()`；多语句经济操作全部置于 `db.transaction()`。
5. 旧存档不重置，新增列使用 `_ensure_column()`，新增表使用 `CREATE TABLE IF NOT EXISTS`，结构重塑使用幂等 `_migrate_*()`。
6. 所有用户可见文案、代码注释和文档字符串使用中文，并保持现有修仙语气；普通页面、实体页面和 RichPage 继续遵守项目展示规范。

### （二）实施方式

每份里程碑计划均以可独立验收的软件增量为边界。M4 和 M6 因含独立子系统或双发布迁移，拆分为两份计划：

## 二、代码审查结论

### （一）可直接复用的现有能力

| 现有落点 | 四期复用方式 |
|---|---|
| `config/realms.py` 的 len 驱动推进 | 追加 realm 6 后，`next_stage()`、`is_big_breakthrough()` 和溢出顶点自动上移 |
| `services/breakthrough.py` 的三段渡劫会话 | 增加 target realm 6 的天人劫分流，第三段继续自动提供“直面心魔” |
| `models/db.py` 双连接与写锁 | 灵兽状态、奇遇结算、征途楼层、镇妖塔首通、洞府升级均复用同一事务边界 |
| `handlers/common.py` 一次性 token | 捕捉、放生、守猎、征途、镇妖塔、洞府全部继续走 15 分钟一次性动作令牌 |
| `services/notifications.py` | 扩为守猎、链式奇遇、灵田三个通知扫描器，统一重试上限 5 次 |
| `services/auction.py` 实例托管 | 新增 `kind='beast'`，复用挂拍费、escrow、防狙击、buyout、结算与审计 |
| `services/combat.py` 确定性引擎 | 以可选支援单位扩展，不传支援时保持原结果和日志不变 |
| `bot/presentation.py` 与 RichPage | 新玩法的长战报、征途结算和排行播报复用现有展示层 |
| `services/game_events.py` | 合体突破、稀有兽、链式大机缘、百层首通继续通过统一领域事件分发 |

### （二）必须处理的真实代码差异

1. 当前 `config/events.py:ENCOUNTERS` 是旧版字典式选项，且历练在**出发时**预生成事件并把事件写入 `explore_runs`。M3 必须改为结算后触发的 `adventure_choices`，同时保留旧列和旧 callback 兼容路径，直至所有部署前在途历练自然结清。
2. 当前 `character_skills` 只保存已装备槽，学习新技能会覆盖槽位。M6A 不能直接切读；必须先扩表、回填、双写并观察至少一个发布周期。
3. 当前 `services/combat._act()` 在角色被定身时只写日志后返回，未暴露“本回合是否行动”。M2 支援单位必须让 `_act()` 返回行动结果，才能保证主人被定身时灵兽同步蛰伏。
4. 当前灵兽捕捉机会无需新增业务表：结算结果返回 `species_key`，handler 将其编码到一次性 token 的 action 中；token 到期即视为灵兽遁走，且不变更捕捉保底。
5. 当前 `notifications.notify_ready_actions()` 只扫描历练和秘境。新增提醒应继续集中在该服务，避免各业务服务各自直接调用 Telegram。
6. 当前 `services/quests.py` 已有按 period 分片的幂等进度表。M5 洞府每周征途令可复用 `quest_progress` 作为一次性发放账本，不新增单用途周表。
7. 当前所有实际战斗调用点只有历练、秘境、世界 Boss、PvP 和宗门战；四期新增征途、镇妖塔。M2 先覆盖 PvE 与世界 Boss，M4 覆盖新玩法，M6B 最后覆盖 PvP 与宗门战。

## 三、跨里程碑架构约束

| 约束 | 统一落地口径 |
|---|---|
| 存档兼容 | 不删除旧表、旧列；M6 旧技能表保留至 v4.1，旧历练奇遇列至少保留至 v4.1 |
| 前台活动冲突 | 征途视为前台战斗活动；开始闭关、历练、秘境或恢复丹操作时均检查 active expedition，避免快照被后续操作覆盖 |
| 支援单位状态 | `active_beast_id` 仅可指向本人 `status='idle'` 的灵兽；守猎、拍卖、放生必须在同一事务内清理或拒绝出战引用 |
| 资源绑定 | 守猎、兽魂、灵田普通产出、征途主要材料默认 `bound=1`；灵田精品使用独立 item_key 且 `bound=0` |
| 通知幂等 | 每个通知表均保存 `notified_at`、`notify_attempts`；成功后不再发，失败第 5 次标记终止，新任务重置两字段 |
| 配置纯度 | `config/beasts.py`、`config/estate.py`、`config/tower.py` 只放静态数据；不得导入 service、handler 或 DB |
| 事件一致性 | 新奇遇触发时把事件选项快照写入 `adventure_choices.state`，结算不依赖会话期间可能变化的配置 |
| Rich 展示 | 征途、镇妖塔、奇遇终局和 PvP 战报使用 RichPage；动态角色名、灵兽名、掉落名均转义 |
| 数值护栏 | 灵兽 DPS≤同档 GEARED 15%，灵兽治疗≤主人 max_hp 3%/回合，灵田单格最大价值≤当档日收益 30% |
| 日常负担 | M4 和 M6B 各执行一次周事件总量审计，新增每日主动操作目标不超过 5 分钟 |

## 四、发布与回滚安排

### （一）发布批次

| 批次 | 数据迁移 | 功能开关 | 回滚边界 |
|---|---|---|---|
| M0—M1 | 仅新增配置、合体内容与一次性迁移标记 | 直接开放 | 回滚代码不会丢失新存档字段；已进合体角色不可降境回滚 |
| M2—M5 | 新表、新列均为加法迁移 | 各命令随 router 注册开放 | 回滚时保留表数据；旧代码忽略新增表 |
| M6A | 建新技能表、回填、双写 | 不开放第 4 槽和新神通 | 可回滚到旧表读取，镜像表保留 |
| M6B | 读取切新表、停止旧表写入 | 开放第 4 槽与新神通 | 若回滚，需先恢复双写版本；禁止直接回到 M6A 之前版本 |

### （二）每个里程碑上线前门槛

1. `.venv/bin/python -m pytest` 全绿。
2. 数值里程碑的 `.venv/bin/python -m tools.balance_sim` 无越线警告。
3. 迁移在同一旧库上连续执行两次，结构与数据计数一致。
4. 所有 state-changing callback 有一次性 token 测试和并发/重复点击测试。
5. 通知任务有“成功一次、失败最多 5 次、重置后可再次通知”测试。
6. 用户指南、帮助页、命令列表和版本公告与实际开放功能一致。
